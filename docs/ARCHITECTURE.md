# Архитектура

## Реализовано
- genetics/GeneticsSavedData — серверный файл Players и Season, версия3. Один UUID — одна наследственность.
- genetics/SeasonLedger — регистрация, единственный выбор, монотонные номера, архив.
- energy/EnergyRules — чистая миграция NBT, формула, онлайн-тик, доступный выход.
- energy/CursedEnergy — доступ к SavedData, транзакция расхода, общее окно выхода20тиков, синхронизация.
- energy/EnergyReinforcement — поддерживаемые серверные модификаторы тела.
- network/CharacterNetwork — команды намерения, разрешения, ограничение частоты, публичные снимки.
- client — клавиши, меню, HUD; серверные пакеты не импортируют клиентские классы.
- commands/SeasonCommands — операторский жизненный цикл сезона.
- FoundationConfig — серверные предложенные значения, отдельно от старого MDK Config.
- techniques, curses, world, builder — существующие подсистемы сохранены.

Профиль пока агрегирован двумя SavedData, а не перенесён в новый монолит:
`jujutsurpg_genetics.dat` и `jujutsurpg_energy.dat` в overworld/data.
Сезон и право Шести глаз лежат вместе с генетикой, чтобы избежать рассогласованных сохранений
двух отдельных файлов при назначении. CE не хранит копию сезонного права, а проверяет реестр.
Логика исполняется на потоке сервера; конкурентные сетевые намерения сериализуются Forge.
Транзиентные окна расхода принадлежат экземпляру SavedData мира, а не глобальной статической карте.

PersistentStore учитывает перехват ошибок загрузки внутри Minecraft: если файл уже существует,
но загрузчик вернул null, новое пустое хранилище не создаётся. Ошибка останавливает операцию;
администратор должен восстановить резервную копию или совместимую версию мода.
Некорректный тип существующего профиля также не превращается в новый случайный профиль.

## Целевая структура, ещё не реализовано
PlayerSnapshot объединит доступную игроку проекцию существующих хранилищ.
ProgressionService хранит пять отдельных навыков, испытания и отдельное владение техникой.
AbilityService принимает ID и намерение, проверяет наследственность/освоение/цели,
затем вызывает CE-транзакцию и серверный эффект. Фазы: request → validate → debit → execute → end.
Поддерживаемые способности используют тот же расход без отправки полного профиля каждый тик.
Будущие SummonService/DomainService/QuestService получают контекст владельца и жизненный цикл;
они не меняют генетику и не присваивают XP напрямую.

Не создаём пустые классы для19модулей. Извлекаем интерфейс при появлении второго реального потребителя.
Временные эффекты, постоянный прогресс и секретная генетика должны иметь отдельные представления.


## Реализованный модуль clans (2.0)
ClanDefinition/ClanRegistry содержат только общедоступные определения; Clan стал объектом
со стабильным ID. Новый путь регистрируется без изменения центральной логики выбора.
GeneticsSavedData.selectOrigin создаёт полный профиль один раз; getProfile лишь читает/мигрирует.
ClanSelectionService обеспечивает серверное ожидание; ClanNetwork переносит намерения владельца
соединения и публичный View, без секретной техники. CharacterNetwork теперь protocol10,
дополнительный канал clans имеет protocol1.
ClanProgression хранит независимый журнал и транзакцию награды; TrainingChallenge выдаёт
одноразовые билеты шагов; ClanTrainingService проверяет позицию, действие, срок и CE.
Сессии отделены от постоянного прогресса и очищаются при выходе/остановке сервера.
ClanClient, ClanSelectionScreen и ClanScreen существуют только на физическом клиенте.
Общие классы не импортируют net.minecraft.client; проверено запуском GameTestServer.
